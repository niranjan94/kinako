# Fork maintenance

This repository is a fork of [pingdotgg/t3code](https://github.com/pingdotgg/t3code) that ships as **Kinako**, with its own builds, and sends no traffic to upstream's infrastructure. It installs and runs alongside upstream T3 Code without sharing any state. Remote access is LAN, Tailscale, and SSH only; T3 Connect is not built in.

## Syncing with upstream

`main` holds upstream plus this fork's changes. Upstream comes in by merging, never rebasing, so history keeps its real order and `main` is never rewritten:

```bash
git remote add upstream https://github.com/pingdotgg/t3code.git   # once
git fetch upstream
git checkout main && git pull
git merge upstream/main
git push origin main
```

Resolving conflicts:

- `pnpm-lock.yaml`: never hand-merge it. Take upstream's copy (`git checkout --theirs pnpm-lock.yaml`), then run `pnpm install` to regenerate it.
- `.github/workflows/ci.yml`: take upstream's copy (`git checkout --theirs .github/workflows/ci.yml`), then rerun the CI substitutions below.
- `README.md`: keep this fork's copy (`git checkout --ours README.md`), then port anything from upstream's change that still applies, such as new providers or docs links.

Agents should use the `merge-upstream` skill (`.agents/skills/merge-upstream/`), which scans upstream for changes that touch Kinako's identity before merging and lists the known resolutions.

`git diff upstream/main...main` shows everything this fork changes. Merge before cutting a release so it carries upstream's latest fixes. Check the Actions tab after merging and disable any workflow upstream added.

Merge conflicts come from fork changes that touch the same lines as upstream. Keep new patches out of `package.json` versions, `pnpm-lock.yaml`, upstream workflows, and busy UI files. Prefer new fork-only files and environment variables.

Fork-only migrations live in `apps/server/src/persistence/Migrations/fork/` and record into their own `fork_sql_migrations` ledger (`ForkMigrations.ts`), so upstream migrations keep upstream's ids and merge without renumbering. Fork migrations run after every upstream migration; give a new one the next fork id and record the latest upstream id beside it in `firstRanAfterUpstream` (`ForkMigrations.test.ts`), which checks that later upstream migrations never drop fork schema from existing databases. Builds before this split recorded fork migrations in upstream's ledger at shifted ids; `splitForkMigrationLedger` moves them once on startup, and those older builds refuse to open the database afterwards. The mobile store promotion row is omitted until Kinako has public distribution links.

## Rebrand seams

Kinako's identity lives in `packages/shared/src/forkBrand.ts`. Call sites import from it instead of carrying literals, so most upstream changes merge cleanly; a conflict on one of these lines usually means upstream touched the same literal, and the fix is to keep the import. Internal names stay upstream's on purpose: the `@t3tools/*` scope, contract names, and `T3CODE_*` environment variables. Text only agents read also keeps upstream's "T3 Code": MCP tool names and descriptions, the MCP server name, MCP errors returned to agents, and prompts injected into turns such as pull request watch wakes. Commands, paths, and repository URLs inside that text still use Kinako's values, since an agent has to be able to run them. The worktree-local dev state directory is `.kinako` like the home directory; `.t3` stays in `.gitignore` so older worktrees' data is not committed.

## Moving from T3 Code to Kinako

Earlier builds of this fork installed as T3 Code and kept their data in `~/.t3`. To move once:

1. Stop the old install: quit the desktop app and run `t3 service uninstall` if you installed the background service.
2. Move the data: `mv ~/.t3 ~/.kinako`. If upstream T3 Code also uses `~/.t3` on this machine, copy instead (`cp -a ~/.t3 ~/.kinako`) and leave upstream's copy alone.
3. Remove the old launcher and app: `rm ~/.local/bin/t3` (if it points into `~/.t3`) and delete the old `T3 Code (Nightly)` app.
4. Install Kinako: `curl -fsSL https://raw.githubusercontent.com/niranjan94/kinako/main/scripts/install.sh | T3CODE_CHANNEL=nightly sh`, then `kinako service install` if you want the background service, and install the Kinako desktop app.

What does not carry over:

- **Saved remote environments in the desktop app** are encrypted with a key tied to the app's name on macOS and Linux. Delete `~/.kinako/userdata/connection-catalog.json` before the first launch and add them again.
- **Paired phones and browsers** stored the old port (3773) and `t3code://` links. Pair them again against port 3873.
- **The "No project" Scratch project** is recorded at `~/.t3/scratch`. Kinako creates a new one under `~/.kinako/scratch`; archive the old entry. Screenshots in older messages also link to `~/.t3/userdata`.
- **SnapShot setup** on Linux (GNOME extension, KDE and Hyprland helpers, Niri and Hyprland bindings) installs under new names. Run setup again from Settings, and remove the old `snap-shot@t3.codes` extension and old bindings unless upstream T3 Code uses them.

Nothing migrates automatically: Kinako never reads `~/.t3` or upstream's desktop profiles (`t3code`, `t3code-v2`), so desktop drafts, layout, and theme start fresh. If you use Tailscale Serve, it now defaults to port 8443.

## CI

Upstream's `ci.yml` runs unchanged except for its runners. GitHub's standard runners are free for public repositories but have half the cores of upstream's Blacksmith machines, so job timeouts are doubled, and so is the web suite's 15 s per-test timeout, which the heaviest browser tests otherwise hit on these runners. The substitutions are safe to rerun:

```bash
perl -pi -e 'if (s/blacksmith-\d+vcpu-ubuntu-2404/ubuntu-24.04/ || s/blacksmith-\d+vcpu-macos-26/macos-26/) { $d = 1; next } if ($d && s/^(    timeout-minutes: )(\d+)$/$1 . $2 * 2/e) { $d = 0 }' .github/workflows/ci.yml
perl -pi -e 's/^(        run: vp run --filter \@t3tools\/web test)$/$1 --testTimeout=30000 --hookTimeout=30000/' .github/workflows/ci.yml
```

CI and `fork-release.yml` use Ubuntu 24.04, matching upstream. Playwright does not support Ubuntu 26.04 yet, so the server browser tests cannot install Chromium there. Linux release artifacts also link against the build machine's glibc, so a 26.04 build would not start on older distributions.

## One-time setup

1. **Actions:** enable Actions for the fork, then disable every upstream workflow except `ci.yml`, `release-desktop.yml`, and `agent-context-budget.yml`. The others expect upstream's runners, secrets, and accounts, and would otherwise queue or fail on every push. `agent-context-budget.yml` fails a pull request that grows `agentContextBudget.json` past `main`'s unless it carries the `agent-context-increase` label, and the fork's own `fork-agent-context-budget.yml` does the same for `agentContextBudget.fork.json`, which holds the bytes Kinako's tools add. Create that label in the fork. `fork-release.yml` calls `release-desktop.yml` and `fork-ios.yml`.

   ```bash
   gh workflow list --repo niranjan94/kinako --all --json path --jq '.[].path' \
     | grep -v -e '/ci.yml$' -e fork-release.yml -e fork-ios.yml -e release-desktop.yml -e agent-context-budget.yml \
     | xargs -n1 basename | xargs -I{} gh workflow disable {} --repo niranjan94/kinako
   ```

2. **npm:** `fork-release.yml` publishes `kinako-cli` with npm trusted publishing, so it needs no token, but npm only lets you register a trusted publisher on a package that already exists. Publish the first version by hand while logged in to npm, using the version of an existing nightly release (its tag without the `v`): `node scripts/build-npm-launcher.ts --version <version> && npm publish --access public --tag nightly npm-packages/kinako-cli.tgz`. Then on npmjs.com, under the package's **Settings → Trusted publishing**, add GitHub Actions with repository `niranjan94/kinako` and workflow `fork-release.yml`, with **Allow npm publish** enabled. Until then the **Publish CLI to npm** job fails; the GitHub release and iOS build are unaffected. Complete its first successful workflow publish within two days of creating the trust configuration, or npm expires it. After verifying OIDC publishing works, set the package's **Publishing access** to **Require two-factor authentication and disallow tokens**, as [npm recommends](https://docs.npmjs.com/trusted-publishers/).

## Releasing

This fork ships nightlies only: `main` tracks upstream's `main`, not its release tags, so its builds match upstream's nightly train rather than a stable version.

Actions → **Fork release** → Run workflow on `main`, usually after merging upstream and seeing CI pass. The version follows upstream's nightly scheme, `<next patch>-nightly.<UTC date>.<run number>` (for example `0.0.46-nightly.20261013.4`), and the release is published here as a prerelease named `Kinako Nightly <version> (<commit>)`. The workflow builds macOS, Windows, and Linux installers plus CLI archives.

- Install the CLI with `curl -fsSL https://raw.githubusercontent.com/niranjan94/kinako/main/scripts/install.sh | T3CODE_CHANNEL=nightly sh`. Without it the script installs from the stable channel, which this fork does not publish. An installed nightly CLI updates along the nightly channel on its own.
- If only npm publishing fails, rerun **Fork release** on `main` with **cli_release_version** set to the existing release version without `v`. This verifies the release and its checksums and publishes only the launcher, without rebuilding desktop or iOS. It can run while the original iOS job finishes.
- After the GitHub release, the same version is published to npm as `kinako-cli` under the `nightly` dist-tag, so `npx kinako-cli@nightly` runs it. The workflow publishes only from this repository's `main`, uses npm OIDC trusted publishing with provenance on a GitHub-hosted runner, and builds the launcher from an uncached frozen-lockfile install. Its generated manifest points to this public repository, as npm provenance requires. The workflow updates only `nightly`, so use `@nightly` explicitly rather than relying on `latest`.
- The desktop app installs as **Kinako (Nightly)** and follows the nightly update channel on every platform.
- macOS builds are signed and notarized, so they open without warnings. Windows installers are unsigned: SmartScreen warns, choose **More info → Run anyway**.

## Mobile releases

iOS ships to TestFlight only as part of a nightly: once `fork-release.yml` publishes the GitHub release, it calls `fork-ios.yml`, which builds the production variant with `eas build --local` on a GitHub macOS runner and uploads it with `eas submit` to the App Store Connect app `6822450068`. Building on GitHub's runner spends no EAS build credits; EAS only stores the signing credentials and the App Store Connect API key and assigns the build number. Every build lands in the internal TestFlight group "Kinako Nightly", which has automatic distribution on. The marketing version is `version` in `apps/mobile/app.config.ts`. CI on each commit uses nothing from EAS, and upstream's `mobile-eas-*` workflows stay disabled. No over-the-air updates are published.

The job skips itself without the `EXPO_TOKEN` secret, an access token named "kinako-ci" on the `niranjan94` Expo account. Signing is set up by hand rather than through `eas credentials`:

- Apple Developer portal: App IDs `io.niranjan.kinako` (App Groups, Associated Domains, Push Notifications, Sign in with Apple), `io.niranjan.kinako.widgets` and `io.niranjan.kinako.sharing` (App Groups), all in app group `group.io.niranjan.kinako`. Each has an App Store profile ("Kinako iOS App Store", "Kinako iOS Widgets App Store", "Kinako iOS Share Extension App Store") on the iOS Distribution certificate `11F00A1A…`, all expiring 2027-06-02.
- expo.dev → kinako → Credentials: one iOS entry per bundle ID with that certificate (already stored on the account), its uploaded profile, and the account's "EAS" App Store Connect API key (`87C7QBTG4T`) for submission.

When the profiles expire, or after changing a capability on any of these App IDs, regenerate the affected profiles in the portal and upload them to the matching expo.dev entries. Changing a capability on `io.niranjan.kinako` also invalidates the desktop "Kinako Developer ID" profile: regenerate it and update `MACOS_PROVISIONING_PROFILE` with `base64 -i Kinako_Developer_ID.provisionprofile | tr -d '\n' | gh secret set MACOS_PROVISIONING_PROFILE`.

The production bundle ID is also the desktop App ID. EAS turns off any App ID capability missing from the iOS entitlements, so the app declares `webcredentials:kinako.niranjan.io` to keep Associated Domains on for the desktop Developer ID profile.

## Signing

### macOS

`release-desktop.yml` signs and notarizes whenever the secrets below are present. Signing uses a Developer ID Application certificate created only for CI (`5RKVW6D5F2`, team `6456AUQBLS`, G2 intermediate, expires 2031-09-17), not the maintainer's personal one, so revoking it affects nothing else. Its private key exists only in the `CSC_LINK` secret.

| Name                         | Kind     | Holds                                                                                                                                      |
| ---------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `CSC_LINK`                   | secret   | Base64 `.p12` of the CI certificate and its key                                                                                            |
| `CSC_KEY_PASSWORD`           | secret   | Password of that `.p12`                                                                                                                    |
| `MACOS_PROVISIONING_PROFILE` | secret   | Base64 Developer ID profile "Kinako Developer ID" for App ID `io.niranjan.kinako` (Associated Domains enabled), tied to the CI certificate |
| `APPLE_API_KEY`              | secret   | Contents of the App Store Connect team key "Kinako notarization" (`.p8`, Developer role)                                                   |
| `APPLE_API_KEY_ID`           | secret   | `38ZR36XBRG`                                                                                                                               |
| `APPLE_API_ISSUER`           | secret   | Issuer ID shown on App Store Connect → Users and Access → Integrations                                                                     |
| `APPLE_TEAM_ID`              | variable | `6456AUQBLS`                                                                                                                               |
| `CLERK_PASSKEY_RP_DOMAINS`   | variable | `kinako.niranjan.io`                                                                                                                       |

A signed build refuses to start without a passkey domain, which upstream derives from its Clerk key. Without Clerk the fork names `kinako.niranjan.io`. GitHub Pages serves it from the `gh-pages` branch, which holds only the `apple-app-site-association` file (`webcredentials` for the desktop app and the three iOS bundle IDs) and the `CNAME`. Edit that branch when the bundle IDs change.

To replace the certificate (expiry, leak, or loss):

1. Generate a key and CSR locally with `openssl`, leaving the email out of the subject.
2. In Certificates, Identifiers & Profiles, create a **Developer ID Application** certificate on the **G2 Sub-CA** from the CSR, and revoke the old one.
3. Edit the "Kinako Developer ID" profile to use the new certificate and download it.
4. Bundle the key and certificate into a `.p12` with `openssl pkcs12 -export`, then update `CSC_LINK`, `CSC_KEY_PASSWORD`, and `MACOS_PROVISIONING_PROFILE`. Delete the local files.

Apps already notarized keep working after the certificate expires; only new builds need the replacement.

### Windows

Unsigned. Adding the Azure Trusted Signing secrets that `release-desktop.yml` reads (`AZURE_*`) turns it on without workflow changes.
